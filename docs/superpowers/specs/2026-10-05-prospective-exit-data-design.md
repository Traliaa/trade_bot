# Сбор данных будущих сделок для исследования выходов

Статус: письменная спецификация для проверки пользователем, не реализация.
5 октября пользователь согласовал комбинированную схему и разрешил небольшую
доработку бота для сохранения снимков без изменения входов, риска и выходов.
Запуск процесса, выдача новых прав, миграция production и деплой не выполнялись.

## Цель и критерий успеха

Для новых фактических входов получать проверяемый материал для будущего
сравнения A/B/C: текущая модель выходов, runner с ранним partial, runner с первым
partial на 3R. Результат этого этапа — данные с происхождением и отчёт покрытия,
не новая торговая стратегия и не обещание прибыли.

Этот проект устраняет пробелы из [проверки покрытия](../../exit-research-coverage-2026-10-05.md).
Старые сделки не получают новые «исторические» значения задним числом.
Предыдущий план реального сравнения остаётся заблокированным до повторной
проверки данных и согласования адаптера v2. Здесь проектируется только capture,
изолированный collector и исследовательский bundle, не сами профили A/B/C.

## Выбранный подход

Минимальный capture внутри бота плюс отдельный read-only collector.
Только внешнее чтение БД не фиксирует реально использованные настройки на входе;
встраивание всей загрузки архивов в бота связывает исследование с торговлей.
Поэтому бот сохраняет наблюдаемые параметры существующего расчёта, а сеть,
пагинация, сверка и исследовательские файлы принадлежат отдельному процессу.

Не менять сигналы, размеры, лимиты, плечо, исходные SL/TP, правила сопровождения,
набор анализируемых монет, уведомления о сделках и ежедневную проверку.
Не открывать дополнительные сделки ради выборки. Новый интерфейс/админка,
Kafka, непрерывная запись стакана всего рынка и автоматический тюнинг не нужны.

## 1. Неизменяемый снимок входа

В существующую `trade_history` добавить nullable JSONB-колонку
`research_entry_snapshot`. Создаётся вместе с записью сделки в уже существующем
INSERT, без отдельного сетевого запроса или отдельной транзакции capture.
`payload` остаётся текущим состоянием сделки. Обычные update/close запросы
не изменяют новую колонку; импорт snapshot в mutable payload запрещён.
Старые строки имеют NULL, старый бинарник после additive-миграции продолжает
работать. Откат приложения не удаляет исследовательские данные.

Snapshot schema=1 содержит только явный whitelist:

- Случайный `capture_id`, не производный от account/order/trade/Telegram ID;
  версия схемы, revision/build identity и флаг dirty/unknown build.
- Инструмент, сторона, timeframe, время наблюдения источников и идентификатор
  исследовательского протокола. Ссылки на секреты и сами секреты отсутствуют.
- Вход, исходный размер, исходные SL/TP и RiskDist именно из успешной операции;
  отдельно исходные значения расчёта и фактические исполнения. Должна быть
  видна разница между planned и filled, её нельзя исправлять незаметно.
- Metadata из того ответа, который реально использован при расчёте: tick/lot/min,
  effective ctVal, ctVal/ctMult исходного ответа, тип контракта и валюта расчёта;
  response-received timestamp, exchange timestamp если предоставлен.
- Полный набор исследуемых BE/LOCK/partial/time/stale-полей, включая нулевые
  значения и false. Отдельно raw-поля и применённые defaults, в том числе
  результат существующего `GetStaleConfig`; никаких `omitempty` внутри контракта.
- Время начала/окончания входных исполнений, источник времени EntryAt и признак
  полноты fills. Локальный fallback времени не объявляется биржевым временем.
- `capture_status` и коды причин неполноты/расхождения; checksum канонического
  whitelist-содержимого. Checksum выявляет изменение, не доказывает истинность.

### Точка наблюдения и неизменность торговли

Сегодня `tradeConfigSnapshot` повторно читает настройки после открытия позиции,
а `CalcTradeParamsV3` и sizing отдельно вызывают `SettingsSnapshot`. Capture
должен передавать копии фактически прочитанных параметров вместе с результатом
расчёта, не перечитывать их позднее и не сохранять весь `models.Settings`.
При несовпадении наблюдаемых версий/хешей relevant-полей запись получает
`settings_changed_during_entry`, а не выдуманный единый effective config.
Нельзя менять порядок существующих чтений/ветвления расчёта ради исследования.

Raw десятичные строки metadata сохраняются рядом с уже используемыми float
значениями без изменения математических операций бота. Отсутствующая строка
не восстанавливается как будто исходная из float. Поля допускают incomplete.

Capture собирается локально из имеющихся результатов, имеет ограничение 32 KiB
и выключатель `RESEARCH_CAPTURE_ENABLED=false` по умолчанию. Нет дополнительной
очереди, фонового worker или GET в критическом пути входа/защиты. Ошибка
формирования/размера snapshot даёт NULL и агрегированный счётчик ошибки, но не
отменяет запись сделки, ордер или сопровождение. Существующая ошибка записи
самой сделки остаётся существующей ошибкой; полной гарантии отсутствия влияния
БД не заявляем. Дополнительные байты INSERT проверяются нагрузочным тестом.
Идентификатор протокола задаётся явно при включении capture; незаданный или
несовпадающий с manifest протокол не становится пригодной выборкой. При NULL
snapshot collector учитывает пропуск в агрегате покрытия, но не придумывает
capture_id или исторический снимок задним числом.

## 2. Отдельный процесс сбора

Новый CLI/service `cmd/research-collect` не импортирует запуск торгового сервиса.
По умолчанию выполняет один проход и завершается; постоянный режим возможен
только отдельным явным параметром и отдельным согласованным запуском.

Входы процесса:

- Подтверждённый protocol manifest: UTC начало/конец включения входов, horizon=72h,
  версии форматов, лимиты ресурсов. Время старта не назначается задним числом.
- SELECT-доступ к записям только согласованного аккаунта через ограниченную
  роль/view; collector не читает `user_settings` и не получает ключи из БД.
- Отдельный OKX ключ с правом Read, без Trade/Withdraw; секреты передаются через
  inherited FD/скрытый ввод и остаются в памяти. При отсутствии такого доступа
  приватная сверка остаётся pending; существующий торговый ключ автоматически
  не используется. Подготовка доступа — отдельное действие перед запуском.
- Явно заданный приватный каталог на отдельном volume, не git и не web-root.

Доступ к БД только read-only repeatable-read для одного короткого прохода;
сетевые запросы не удерживают DB-транзакцию. Снимок строк прохода фиксируется
в памяти; приватные идентификаторы используются только для связи и сверки.
Capture ID связывает обезличенные результаты между проходами. Повторный запуск
повторно получает нужные приватные fills, а не хранит private cursor в файле.

Collector получает:

1. Архивные fills: исходные decimal-строки цены/размера/fee/PnL, `feeCcy`, фактическое
   время исполнения. Сверяет связь с ордерами записи, дедупликацию и сохранение
   объёма; частичная фиксация определяется исполнениями, не `took_partial`.
   Внутренние ID после сверки заменяются обезличенной нумерацией в bundle.
2. Рыночные сделки для неполных первой и последней минут, закрытые 1m между ними.
   Цена до EntryAt не используется как бар после входа; продолжаем сбор до
   EntryAt+72h независимо от фактического закрытия позиции.
3. Исторические realized funding rates и доступные данные mark. 1m mark OHLC
   сохраняется как приближение, не как доказанный settlement mark. Без точного
   источника затрат статус остаётся sensitivity-only, а не «funding=0».
4. Metadata-наблюдения по участвующим инструментам при проходах. Они показывают
   только наблюдаемые изменения, не гарантируют отсутствие изменений между
   опросами. Для будущего replay фиксированные ограничения на входе должны
   называться модельным допущением; точная временная история требует отдельного
   источника. Изменения условий и неизвестные интервалы видны в coverage.

Реальная торговля может менять настройки после входа. Bundle сохраняет исходный
snapshot для фиксированных A/B/C; это не полное воспроизведение live-выходов.
Журнал всех последующих конфигурационных изменений и V3 callback в этот этап
не включён. Actual ledger показывается отдельно от будущего модельного результата.

## 3. Bundle и точный горизонт

Новый формат `prospective-exit-bundle-v1` не выдаётся за `ExitDataset` schema=1.
В существующий валидатор данные автоматически не подаются и он не ослабляется.
Manifest, snapshot, нормализованные fills, market segments и coverage содержат
версии, UTC timestamps, источники и checksum безопасного содержимого.

EntryAt — сохранённое биржевое время входа. Если вход собран из fills с разными
временами, bundle сохраняет их все и помечает `multi_time_entry`: правило
превращения такого исполнения в один вход replay не выбирается молча.
EndAt = EntryAt+72h без округления. Рынок делится на непересекающиеся интервалы
`[EntryAt,nextMinute)`, полные минуты, `[floorMinute(EndAt),EndAt)`;
пустые граничные интервалы при выровненном времени отсутствуют.
Timestamp ровно на правой границе относится к следующему интервалу; данные
после EndAt не попадают в OHLC. Полнота сегмента и фактическое отсутствие сделок
различаются. OHLC без наблюдаемых цен не создаётся искусственно.

Первая/последняя неполные минуты обозначены `boundary_segment`, а не обычный
закрытый 1m bar. Будущий replay v2 должен отдельно определить обработку
защитных касаний, funding ровно на границе и pending-решений на конце горизонта;
эта спецификация сохраняет исходные данные, но не меняет действующую симуляцию.

## 4. Отказы, ресурсы и доступ

Один collector writer, lock приватного каталога; второй экземпляр отказывается
стартовать. Каталог 0700, файлы 0600, атомарная запись/rename и проверка checksum
при возобновлении; повреждённые файлы не принимаются как готовые и не затираются.
Новые версии данных добавляются отдельно; manifest связывает версии.

Предлагаемые консервативные defaults: один сетевой запрос одновременно, до 1 GET/s,
таймаут 15s, до 3 повторов transient-ошибки с backoff/Retry-After, до 200 страниц
одного компонента sample за проход и до 10000 запросов/сутки. HTTP redirects
запрещены; allowlist методов/hosts/paths, размер ответа ограничен 4 MiB.
Пагинация контролирует повтор cursors, дубликаты, полноту временного окна.
Достижение лимита — incomplete с продолжением в следующем проходе, не успех.
Public cursor может храниться; приватный cursor/ID — только в памяти.
Для приватных архивов возобновление идёт повторной сверкой ограниченных временных
окон; их границы можно сохранять без private IDs. Насыщенное окно, которое
невозможно полностью получить в пределах бюджета, остаётся incomplete — нельзя
пропустить совпадающие timestamps или бесконечно объявлять один и тот же прогресс.

Дисковый бюджет первого запуска — 1 GiB, включая временные/старые версии;
при исчерпании прекращаются только исследовательские записи. Автоматического
удаления архивов нет. Предлагаемый период включения новых входов — 28 дней
после отдельно согласованного старта, плюс 72h для последнего входа. Это
ограничение расходов и протокол сбора, не обещание достаточной статистики.
Все значения входят в manifest до начала; изменение создаёт новый протокол.

Состояния независимы: capture complete/incomplete/missing; рынок pending/complete/
incomplete; сверка pending/matched/mismatch; costs verified/sensitivity-only/unknown.
Нет общего `verified=true`, скрывающего различия. Если инфраструктура недоступна,
показывать последний успешный проход и возраст данных. Нет Telegram-сообщения
на каждую ошибку: агрегированные безопасные логи и локальный coverage-report.
Не менять существующее расписание мониторинга.

Логи и файлы не содержат DSN, account/Telegram/order/private trade IDs, ключей,
подписей, raw HTTP errors/responses приватных endpoints. Сохранять только whitelist
нормализованных полей; публичные market trade IDs не являются ID сделок аккаунта.
Ошибки указывают код, безопасное имя источника и capture_id. Даже при Read-only
ключе утечка секретов недопустима; ограничение методов не заменяет права на бирже.

## 5. Проверки и порядок включения

- Regression: одинаковые входные данные с capture on/off дают одинаковые торговые
  параметры, порядок/число торговых вызовов и уровни защиты. Snapshot не создаёт
  новых network calls в боте. Неисправность collector не входит в его call graph.
- Снимок копирует использованные значения; defaults/false/zero сохраняются;
  изменение settings во время входа видно как incomplete. Ошибки JSON/oversize
  не блокируют сохранение сделки. Update/close не меняют исходную колонку.
- Миграция additive, старые NULL и старый бинарник совместимы. Проверить размер
  payload и задержку INSERT до включения; реальную миграцию не выполнять тестом.
- Fake HTTP/DB проверяют SELECT/GET-only, redaction секретов, таймауты, пагинацию,
  отмену, quota, отсутствие второго writer и восстановление после обрыва записи.
- Decimal reconciliation: частичные fills, дубли/конфликты, чужие исполнения,
  rebate, неизвестная валюта, переполнение и multi-time entry не скрываются.
- Boundary segments: точная миллисекунда входа/конца, сделки на границах,
  отсутствие цен, разрыв/повтор страниц, ценовой гэп и заполненный 72h горизонт.
- Детерминированный export одинаковых источников/manifest, отсутствие private IDs,
  отдельные статусы и отказ выпускать готовый replay dataset без v2-адаптера.

Сначала локальная реализация и тесты, capture остаётся выключенным. Затем отдельное
согласование миграции, credentials, каталога/лимитов и запуска. После небольшой
контрольной выгрузки — проверка нагрузки, полноты и сверки. Лишь затем старт
зафиксированного prospective-периода. Ни push, ни deploy, ни запуск daemon этой
спецификацией не выполняются автоматически.

После проверки пользователем этой спецификации составляется implementation plan.
Разрешение доработать запись данных не трактуется как одобрение ещё не написанного
плана или как разрешение менять торговую стратегию.
