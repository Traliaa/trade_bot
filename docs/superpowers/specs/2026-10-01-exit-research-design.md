# Сравнение выходов на одинаковых входах: проект исследования

Статус: **на согласовании; реализация не начата**.
Основание: пользователь одобрил исследовательский этап без изменения live-торговли.
Связанная сверка: `docs/strategy-audit-2026-10-01.md`.

## Цель и границы

Установить, улучшает ли согласованное сопровождение после +3R результат
одинаковых входов относительно зафиксированного профиля выходов.
Критерий успеха первого этапа — воспроизводимый и проверенный расчёт,
а не обязательная прибыль выбранного варианта.

Не менять production runner, настройки, риск, UI, БД, ордера и состав торгуемых
инструментов. Не подключать SMC к торговле. Не исправлять спорную историю
автоматически. Учёт общих биржевых позиций — отдельная задача после этой сверки.

## Рассмотренные подходы

1. **Рекомендуется: парное воспроизведение выходов.** Сохранённые проверенные
   входы, размеры и начальные стопы одинаковы для всех профилей. Это изолирует
   влияние сопровождения и не требует выдумывать прошлый список монет.
2. Полный портфельный backtest с повторной генерацией сигналов. Нужен позже:
   разные выходы освобождают лимиты в разное время, поэтому фактические входы
   уже будут различаться. Требуются исторические списки инструментов и метаданные.
3. Сразу сменить стратегию/фильтры в live. Отклонено: смешивает эффекты,
   повышает финансовый риск и не даёт проверяемого сравнения.

Сравнение 20/40/80 инструментов, новых фильтров и SMC — последующие отдельные
исследования. Первый этап не объявляет лучший список монет или новую стратегию.

## Существующий код и ограничения

- `internal/research/replay.go` сейчас моделирует фиксированные SL/TP/time-exit;
  частичных закрытий и production trailing нет. Для V3 здесь SL = 2 ATR,
  тогда как live `sessions/v3.go` использует swing/ATR-guard/fallback.
- `cmd/research` по умолчанию перебирает V3/SMC и лимиты списка. Эта команда
  сохраняет прежнее поведение; отдельный режим сравнения выходов не запускает
  этот перебор автоматически.
- В live есть два источника частичного закрытия: настройки runner и
  `V3PartialCheck` от общего состояния стратегии. Поэтому модель только по
  `PartialTriggerR` нельзя называть точной копией production.
- В репозитории есть только синтетический пример, не готовый проверенный
  исторический датасет для этого сравнения. Срок сбора данных не считать нулевым.

## Входные данные и единица сравнения

Новый локальный формат для парного исследования, отдельный от `Dataset schema=1`.
Он содержит идентификатор примера без account/order ID, инструмент, сторону,
время фактического входа, цену исполнения, исходный SL, фактический исходный TP,
размер, contract value, tick/lot/min size и конфигурацию выходов.
Безопасные метаданные и версии схемы/профиля обязательны.

Для каждой записи обязательны `reconciliation_status`, происхождение данных,
комиссия входа и её валюта. В основное сравнение допускается только `verified`;
прочие перечисляются в exclusions с причинами. Общие/неатрибутированные
позиции, включая AVAX из аудита, не используются для подбора параметров.

Нужны закрытые 1m OHLC со сплошным покрытием, исторические funding-события
с mark price, модель спреда и проскальзывания. Если вход внутри минуты,
её OHLC не раскрывает траекторию после входа: пример исключается с
`intraminute_entry_coverage_missing`, если нет более подробных данных.
Не округлять время входа незаметно и не использовать предшествующий ему high/low.

Историческое funding удержанной фактически позиции нельзя напрямую прикладывать
к контрфактическому выходу: для каждого остатка начислять rate × mark × contracts
× contract value в моменты funding. Неизвестные funding/спреды явно помечаются;
такие результаты — чувствительность к допущениям, не основание для live.

## Профили первого сравнения

Параметры берутся из явного manifest, не из сегодняшних настроек пользователя.
Три фиксированных профиля, без автоматического подбора:

1. `fixed_v1`: исходные SL/TP и фиксированный time-exit; контроль существующей
   исследовательской модели, **не live-baseline**.
2. `configured_trailing_v1`: исходный фиксированный TP, BE/LOCK/partial/time/stale
   по snapshot, без дополнительного callback V3. Это модель настроенного
   сопровождения, **не точная реконструкция всех production-действий**.
3. `runner_3r_v1`: те же правила до +3R, но нет TP полного остатка;
   после активации остаются однократная частичная фиксация и trailing SL.
   Time/stale выходы после активации отключены, как в текущем runner.

Начальный диагностический manifest из последних snapshot: BE с 1R, offset 0,1R;
LOCK с 1,2R, offset 0,6R; partial 50% с 1,25R; time-stop 12 × 15 минут
при current R < 0; early time-stop выключен. Stale-значения фиксируются явно:
16 баров, min MFE 0,35R, exit profit 0,25R, near BE −0,03R,
max adverse −0,65R, grace 6 баров, worse-by 0,30R, tighten-to-BE 0,05R.
Это исходные параметры сравнения, не рекомендация изменить торговлю.

1R = расстояние фактического исходного входа до исходного SL, неизменно.
Runner активируется по закрытию 1m при current R >= 3; LONG SL = close − 1R,
SHORT SL = close + 1R. LONG округляется вниз по tick, SHORT вверх;
лучший существующий стоп не ослабляется. Partial объём округляется вниз;
если закрываемая часть или остаток меньше допустимого минимума, partial
пропускается с причиной, сопровождение SL продолжается.

Configured-профиль повторяет порядок решений `decideTrail15m`, включая
проверки time/stale перед partial/BE/LOCK. Ограничение — не больше одного
успешного действия в 15m-слоте; runner — не больше одного действия на 1m.
Отдельные parity-fixtures фиксируют этот порядок и граничные случаи.
Дополнительный V3 callback не скрывается: его влияние требует отдельной
реконструкции стратегии и выходит за первый этап.

## Модель исполнения без знания будущего

- Сначала на свече проверяются уже действовавшие SL/TP. При касании обоих
  без известного порядка используется SL-first и счётчик неоднозначностей.
- Гэп через стоп исполняется по худшей из цены открытия и уровня стопа,
  затем применяется неблагоприятное проскальзывание/спред.
- По закрытию свечи вычисляются новые решения. Новый стоп действует не раньше
  следующей свечи, не может исполниться задним числом на уже прошедшем low/high.
- Ботские market partial/time-exit исполняются на следующем открытии,
  а не по цене сигнала. Если на этом открытии уже нарушен действующий SL,
  приоритет у закрытия по SL, повторного partial нет.
- В один timestamp funding начисляется на остаток, удержанный непосредственно
  до этого timestamp; вход на этом timestamp не получает прошедший funding.
  Неизвестный порядок исполнения внутри минуты отмечается как допущение.
- Конец данных не превращается в «удачный выход»: незакрытая сделка помечается
  `censored`, её mark-to-market показывается отдельно и не включается в
  статистику закрытых. Для парного итога используются одинаковые завершённые
  примеры, coverage и причины исключения публикуются.

## Архитектура

Добавить в `internal/research` отдельные файлы для exit dataset/валидации,
состояния позиции и решений, исполнения/учёта, парного отчёта. Новый CLI
`cmd/research-exits` читает только локальный JSON; без клиентов OKX, БД,
сетевых запросов и доступа к ключам. Существующий `cmd/research` не меняется.

Состояние хранит отдельно исходный размер, остаток, исходный риск, текущий SL,
MFE, флаги partial/BE/runner/stale и ожидающее исполнения решение.
Ledger хранит каждое исполнение и funding. Итог = сумма gross + signed fees
+ funding; нет повторного списания комиссии входа. Модель исследований
отделена от live-кода, соответствие проверяется fixtures, а не импортом
торговой сессии со всеми её побочными эффектами.

## Отчёт и критерии проверки

В отчёте: SHA-256 датасета, revision/dirty, версия модели, manifest, покрытие,
исключённые/незавершённые примеры, предупреждения, ledger, net/R, win rate,
profit factor, парные разницы результатов, концентрация top-1/top-3.
Контракты и исходный риск одинаковы для вариантов одной записи.
Парная выборка не моделирует капитал/маржу общего портфеля: не выдавать её
за доходность счёта или портфельную просадку. Портфельная проверка — следующий этап.

Обязательные тесты:

- LONG/SHORT, partial один раз, funding после partial по остатку;
- комиссии, rebates и gross/net conservation; исключение чужого/лишнего объёма;
- +3R, откат, запрет ослабления SL, TP до +3R в configured-профиле;
- гэп, stop-first, next-bar активация, market-exit против уже сработавшего стопа;
- tick/lot/min size, недостаточный остаток, NaN/Infinity/недопустимые цены;
- duplicate/gap/future bars, конец данных, intraminute entry;
- воспроизводимость и одинаковый набор входов во всех вариантах;
- полная маркировка отсутствующих funding/спредов и модельных ограничений.

Сначала проверяются синтетические fixtures; их прибыль не трактуется как
рыночное преимущество. Реальные результаты сравниваются на нетронутом периоде,
с отдельным stress-run удвоенных комиссий и проскальзывания. Положительный
результат не запускает торговлю автоматически и не гарантирует будущую прибыль.

## Последовательность после согласования

1. Написать implementation plan для формата, движка и CLI с TDD-проверками.
2. Реализовать и проверить на синтетических обезличенных fixtures.
3. Подготовить проверенный реальный датасет; отдельно сообщить недоступные данные.
4. Выполнить сравнение или честно ограничить выводы при недостаточном покрытии.
5. Только затем проектировать исправление live-выходов, учёта и следующий
   портфельный этап. Любой live-деплой — отдельное решение пользователя.
