## Вывод

Пока нет основания заменять Donchian V3 на Smart Money в реальной торговле. В доступной выгрузке результат отрицательный; название новой стратегии не доказывает преимущество. Приоритет — исправить сопоставимость отбора монет, обеспечить воспроизводимый исторический тест и сравнить кандидатов на одинаковых условиях. Прибыль гарантировать нельзя.

Рассматривается именно число анализируемых монет, не лимит одновременно открытых позиций. В этой работе торговые правила, риск, состав реального списка и настройки сервера не менялись. Добавлена наблюдаемость списка и свежести потоков.

## Проблемы текущего выбора монет

Код: `internal/modules/okx_websocket/service/top_volatile.go`, `service.go`, `internal/models/universe_mode.go`.

1. **Объём сравнивается в разных единицах.** `TopVolatile` напрямую сравнивает `volCcy24h` с порогом 10 млн (conservative) / 5 млн (aggressive) и использует его в рейтинге. У OKX для SWAP это количество базовой валюты, не USDT. Одинаковое число BTC и дешёвых монет означает совершенно разный оборот. Это подтверждённая ошибка сопоставимости ликвидности, а не доказанная единственная причина отсутствия сделок. [Документация OKX, GET Tickers](https://app.okx.com/docs-v5/en/#order-book-trading-market-data-get-tickers).

   Для USDT-SWAP можно начать с явно обозначенной оценки `volCcy24h × last` в USDT. Она не равна точному историческому обороту при изменении цены. Пороги нужно переименовать и откалибровать заново, не механически сохранить старую численную семантику. Проверить одинаковый денежный объём при разных ценах, NaN/Inf и пустые данные.

2. **`watch_top_n` — не общий потолок.** Сначала выбираются N динамических инструментов, затем добавляется фиксированное ядро из 20, дубликаты удаляются. В текущих обоих YAML N=100: теоретический максимум 120, фактическое число меньше из-за фильтров/пересечений. Число 77 из старого сообщения не подтверждает текущее состояние. `WatchTopN` затем перезаписывается фактическим размером — запрошенное и полученное смешиваются. Новый status API хранит эти величины отдельно, но алгоритм отбора не изменён.

3. **Базовые 20 обходят динамические фильтры.** После отбора они безусловно объединяются с результатом. Нужна единая проверка действительности контракта, достаточности истории, ликвидности и свежести и для ядра.

4. **Спред и исполнимость не участвуют в рейтинге.** Bid/ask присутствуют в ответе, но не используются. Рейтинг предпочитает волатильность; это не равно качеству входа. Минимальный контракт может не помещаться в риск небольшого счёта, даже если монета прошла объёмный фильтр.

5. **Список выбирается при запуске.** Периодического обновления в текущем пути нет. Для будущей ротации нужен запас по рейтингу и минимальное время нахождения в списке, иначе подписки будут постоянно переключаться. Открытые позиции должны продолжать сопровождаться независимо от исключения монеты из списка новых входов.

Моя рекомендация для исследования: сравнить **20 / 40 / 80 монет как общий лимит**, а не как добавку к ядру. Это кандидаты для теста, не найденный оптимум. Для всех — одинаковые минимальные требования к данным, ликвидности, спреду и контракту. Не заполнять квоту некачественными монетами ради количества. Проверять доходность, просадку, стоимость исполнения, число независимых возможностей и долю монет со свежими потоками. Увеличение числа монет может добавить коррелированные сигналы и нагрузку, а не преимущество.

## Что представляет собой текущая V3

Код: `internal/modules/strategy/service/service_v3.go`.

Это отбор входов по контексту старшего ТФ, недавнему пробою/ретесту уровня, силе закрытия, размеру импульса, локальной структуре и оценкам long/short. Для входа нужны все обязательные признаки, минимум score и преимущество в 2 балла над противоположной стороной. Есть задержка повторного сигнала на 4 LTF-бара. Поэтому простое снижение `min_confirm_score` не уберёт остальные запреты и может не дать больше входов.

Текущий YAML: LTF 15m / HTF 1h, min score 6, shorts выключены, серверный риск до 0,2%, максимум 3 позиции. Это параметры репозитория, не проверенный снимок production. `htf_conflict` может быть корректным отказом при несогласованном тренде; отменять его только ради частоты нельзя.

Полного воспроизводимого исторического симулятора портфеля в просмотренном репозитории не найдено. Unit-тесты входов полезны для корректности кода, но не подтверждают доходность. Нужен разбор воронки: выбрано → свежие данные → setup → контекст → сигнал → риск/размер → отправка → исполнение. Только fills не содержат пропущенные возможности.

## Как сравнить с Smart Money

Предлагаемые исследовательские варианты, не утверждение о доказанной прибыльности:

| Вариант | Что проверяем |
|---|---|
| A: текущая V3 | Замороженный baseline без подгонки |
| B: V3 + исправленный список | Влияние единых единиц объёма, спреда, свежести и общего лимита |
| C: формализованный liquidity sweep | Снятие ранее известного экстремума → возврат → направленный импульс → пробой локальной структуры → первый ретест |

Для C заранее зафиксировать определение экстремума, величину sweep/импульса через ATR, срок жизни setup, точку отмены и выхода. Использовать только закрытые свечи; подтверждаемый будущими барами swing становится доступен только после подтверждения. Вход на следующем доступном исполнении, не задним числом по выгодной цене той же свечи. Order block/FVG не добавлять автоматически: каждый дополнительный фильтр — отдельная проверяемая гипотеза. Сначала сигнал без реальных ордеров.

## Порядок проверки перед реальной заменой

1. Сохранить версии конфигурации, кода и списка монет, получить актуальные сделки, причины отказов и свечи. Проверить полноту данных после 9 сентября. Не смешивать периоды с разными настройками без меток.
2. Создать replay закрытых свечей и общий симулятор исполнения: комиссии, funding, спред/проскальзывание, `ctVal/lotSz/minSz`, доступная маржа, реальное плечо, ограничения портфеля. При неоднозначном SL/TP внутри свечи — более мелкие данные или консервативное правило. Размеры и правила сопровождения одинаковы между кандидатами.
3. Набрать историю нескольких режимов рынка, ориентир 6–12 месяцев при доступности. Список на каждый момент строить только по данным прошлого; учитывать делистинги и дату появления контрактов. Не применять сегодняшний состав к прошлому незаметно.
4. Зафиксировать малое число вариантов заранее, провести последовательный walk-forward и отдельный нетронутый период. Учитывать число попыток подбора; соседние настройки также должны быть устойчивы. Многократный поиск лучшего результата повышает риск переобучения. [Bailey et al., The Probability of Backtest Overfitting](https://www.davidhbailey.com/dhbpapers/backtest-prob.pdf).
5. Сравнить net expectancy, profit factor, максимальную просадку, tail loss, зависимость от одной монеты/дня, turnover, число сделок и устойчивость к росту издержек. Интервалы неопределённости считать с учётом временной зависимости; одного красивого суммарного PnL недостаточно.
6. Лучший устойчивый вариант — сначала shadow/paper, затем отдельное решение о небольшом live-пилоте с заранее согласованным лимитом потерь. Не увеличивать риск или число открытых позиций ради восстановления убытка. Если преимущества после издержек нет, стратегию не запускать только ради активности.
