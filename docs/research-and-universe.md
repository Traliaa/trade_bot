# Отбор монет, диагностика и исследовательские команды

Реализовано локально 12 сентября 2026. Деплой, миграции и запуск внешнего мониторинга не выполнялись. Этот документ дополняет первоначальный анализ `strategy-review-2026-09-12.md` и описывает уже написанный код, а не результаты исторической доходности.

## Отбор монет

- `strategy.universe.total_limit` — общий потолок. Если поле отсутствует, используется `watch_top_n`, также как общий потолок. Безусловная добавка 20 базовых монет убрана. В обоих YAML оставлен численный лимит 100; вариант 20/40/80 выбирается по результатам исследования, не по предположению.
- Ликвидность: оценка оборота в USDT = `volCcy24h × last`. Это приближение, не точный денежный оборот за сутки. Удалены несопоставимые пороги в количестве монет и фильтр номинальной цены монеты. [Контракт данных OKX](https://app.okx.com/docs-v5/en/#order-book-trading-market-data-get-tickers).
- Единые проверки для всех: конечные положительные числа, статус `live`, базовая валюта `ctVal`, метаданные `ctVal/lotSz/minSz`, свежесть тикера до 2 минут, возраст листинга, диапазон/движение и спред. Нет принудительного заполнения квоты.
- Новые численные пороги — явно заданные исходные параметры для проверки: 10 млн USDT, спред до 20 bps, возраст от 30 дней. Они **не объявляются оптимальными**. Изменение единиц требует сравнения распределений кандидатов на staging перед выкладкой.
- Прогрев больше не ждёт заполнения всей квоты: использует фактически выбранный потокобезопасный список. Общая конфигурация не перезаписывается из market-горутины.
- REST-прогрев принимает только подтверждённые закрытые свечи. Для V3 исторические буферы загружаются без выдачи сигналов; недостаточная история не объявляется успешным прогревом.
- WS проверяет числа и актуальность свечи перед обновлением здоровья потока. Повторные/старые V3-свечи не оцениваются повторно. Входы по свечам старше 90 секунд запрещены, сопровождение 1m продолжает работать.

## Ротация

Реализована, но по умолчанию выключена: `refresh_interval: 0s`. Для staging можно задать `1h`; минимальный интервал ограничен 15 минутами. Параметры `min_residence: 6h` и `retain_bonus: 0.15` уменьшают переключения. Жёсткие фильтры безопасности важнее времени удержания.

Перед продвижением новых монет загружается история LTF/HTF. При ошибке или пустом результате сохраняется прежний список, UI показывает ошибку. Новая монета может попасть в выбранный список до первых live-обновлений, но вход запрещён до свежести всех обязательных ТФ. Проверка повторяется в runner для сигналов, уже находившихся в очереди.

Текущая реализация **сохраняет ранее открытые рыночные подписки** в пределах процесса. Исключённые монеты не допускаются к новым входам, но их 1m продолжают поступать для trailing открытых позиций. Это намеренная безопасная политика вместо преждевременной отписки. Потолок сохранённых символов — 500: при достижении очередная ротация отменяется и отображается ошибка. Автоматическое освобождение подписок после подтверждённого закрытия всех пользовательских позиций — отдельное дальнейшее улучшение. Ротация поддерживает V3; для других стратегий продвижение отклоняется.

## Диагностика и уведомления

`GET /api/strategy/execution` доступен только администратору и возвращает агрегированные счётчики текущего процесса: сигналы, проверки аккаунтов, ограничения, ошибки параметров, попытки ордера, ошибки и открытия. Это не исторический аудит всех действий и не показатели доходности. Экран «От сигнала до сделки» отображает их с обработкой недоступности API.

Обычные отказы по общему/направленному лимиту и уже открытой позиции: первое уведомление приходит сразу, следующие той же причины для того же аккаунта подавляются на 15 минут. При следующем уведомлении после окна указывается число подавленных повторов. Все отказы учитываются в счётчиках. Таймер не присылает пустые сводки. Ошибки и события сделок не подавляются.

## Исследовательский симулятор

Команда `cmd/research` не содержит клиента биржи и не умеет открывать реальные ордера. Два кандидата:

- `v3` — сигналы настоящего V3-кода с зафиксированными параметрами, без autotune;
- `smc` — отдельный автомат: снятие прошлого 20-барного экстремума, возврат, направленный импульс от 0,8 ATR и пробой прошлой 5-барной структуры, затем ретест. Этапы только на разных закрытых барах, setup живёт до 6 баров, противоположный HTF-контекст отменяет его. Live-подключения SMC нет.

Общий исполнитель использует 1m-свечи, вход на открытии следующей доступной минуты, комиссии, спред, проскальзывание, заданные funding-события с историческим mark price, contract value, lot/min size, маржу, ограничение плеча по метаданным и лимит позиций. Размер округляется вниз; невозможный минимальный размер — отказ, не повышение риска. При касании SL и TP в одной минуте первым считается SL, гэп через стоп ухудшает цену. Отсутствие минутных данных внутри открытой сделки — ошибка, не молчаливое заполнение.

**Ограничение модели:** исследование применяет фиксированные stop/target/time-exit. Полная логика live trailing, частичных выходов, приватных margin tiers, ликвидации и реального стакана не воспроизведена. Для V3 стоп = 2 ATR, для SMC — за экстремумом sweep; одинаковы риск, RR и издержки, но не геометрия стопа. Это сравнение исследовательских вариантов, **не точная копия production PnL**. Оба кандидата используют исправленный селектор; прежний ошибочный селектор отдельно не симулируется. Продвижение в live автоматически не выполняется.

В отчёте: параметры, фактическая конфигурация V3, сделки, воронка отказов, net PnL, expectancy, win rate, profit factor, turnover и максимальная просадка equity по доступным минутным ценам. Нет убытков — profit factor `null`, не выдуманная бесконечность. Отмечаются неполные funding-данные. Отчёт CLI содержит SHA-256 исходного датасета и git revision с признаком dirty; для воспроизведения нужно сохранить также сам diff/коммит.

### Формат и запуск

Нужен локальный JSON `Dataset` из `internal/research/types.go`:

- `schema: 1`, текстовый `provenance`, `strategy_config` (Go-имена полей `StrategyConfig`);
- `bars`: `CandleTick` с полями `InstID`, `Start`, `End`, `TimeframeRaw`, OHLC и Volume; даты RFC3339, закрытые 1m/LTF/HTF;
- `snapshots`: исторические `at` и `candidates` по JSON-полям `universe.Candidate`, включая `max_leverage`; котировки/доступность должны быть известны именно тогда, не подставлены из сегодняшнего API;
- `funding`: `at/symbol/rate/mark`, и явный `funding_complete`.

Полный синтетический пример формата:

```sh
go run ./cmd/research -example > /tmp/trade-research-example.json
go run ./cmd/research -input /tmp/trade-research-example.json \
  -start 2025-01-02T05:00:00Z -end 2025-01-02T06:01:00Z -limits 20,40,80
```

Это только демонстрация работы. Выполнена проверка всех 12 сочетаний: 2 стратегии × 3 лимита × обычные/удвоенные комиссии и проскальзывание. Синтетический набор не моделирует полный рынок, и его результаты нельзя использовать для выбора стратегии.

Для реального файла укажите даты нетронутого периода. `-windows 3` делит период на последовательные окна, `-stress=false` отключает удвоенные издержки. Каждое окно начинает с нового баланса и без позиций, более ранние свечи используются для подготовки: это разделённая оценка, не непрерывная кривая счёта и не автоматический подбор параметров. Размер JSON ограничен 128 MiB; длительные исследования требуют разбиения/потокового хранилища.

Добавлен воспроизводимый 95% bootstrap-интервал среднего дневного net PnL: полные UTC-дни, блоки по 3 дня, 1000 повторов, фиксированный seed. Менее 30 дней или 100 сделок — интервал не публикуется. Этот условный интервал не устраняет переобучение, смену режима рынка или модельную ошибку и не гарантирует будущую прибыль.

Исторические котировки/спреды/состав листинга за 6–12 месяцев в репозитории не предоставлены. Они не скачивались и не заменялись современным списком. Полный walk-forward с подбором только на прошлом и live shadow/paper-исполнение ещё не реализованы. Текущая команда — проверяемая основа для них, не доказательство преимущества.

## Независимый монитор

`cmd/healthwatch` запускается **вне контейнера/хоста бота**, иначе падение хоста выключит и наблюдение. Проверяет только `/ready`, не использует биржевые или DB-ключи. По умолчанию опрос каждые 30 секунд, таймаут 5 секунд, 5 минут тишины при старте, подтверждение сбоя 3 неудачами и восстановления 2 успехами.

```sh
go run ./cmd/healthwatch -url https://BOT_BACKEND_HOST/ready \
  -state /var/lib/trade-healthwatch/state.json -interval 30s
```

Каталог состояния нужно создать заранее с правами пользователя монитора. Состояние атомарно сохраняется с правами 0600, рестарт не создаёт новое уведомление уже подтверждённого инцидента. Без `HEALTHWATCH_WEBHOOK_URL` события пишутся только в stdout; с этой переменной отправляется HTTPS POST `{service,state,at}`. Секретный webhook не передавать через аргументы процесса/репозиторий. Нужен получатель, поддерживающий этот JSON, либо адаптер под выбранный мессенджер. Повторная доставка после сбоя возможна: это не exactly-once канал. Ошибки доставки повторяются, URL/секрет не печатаются.

`-once` делает один диагностический запрос и возвращает ненулевой код при недоступности. Монитор **не запускает/не перезапускает бота**, не меняет риск и не выполняет сделки. Он написан и протестирован как программа, но не установлен как системная служба и не запущен на внешнем хосте.

## Проверено и что требуется до выкладки

- Go unit/race-тесты отбора, ротации, приёма свечей, административной защиты, группировки уведомлений, мониторинга, SMC/replay и всего существующего проекта.
- Frontend typecheck, unit-тесты, production build, изолированный браузерный тест тем, компактности, состояния, ключей и новой админской воронки.
- Реальный staging с публичными OKX-данными, приватная исполнимость, PostgreSQL-миграция журнала, интеграция выбранного webhook и производительность длительного backtest ещё требуют проверки. Рыночные пороги и ротацию нельзя считать проверенными на реальной истории по одним unit-тестам.
