# Оформление и состояние бота

Дополнительные изменения отбора монет, ротации, группировки уведомлений, диагностики и исследовательских команд описаны в [research-and-universe.md](research-and-universe.md). Логи production от 12 сентября, 11:00 МСК, подтвердили запуск нового пакета и применение миграции 0006, но прогрев завершился ошибкой. Исправление этой ошибки описано в конце документа; его выкладка ещё требуется.

Изменения от 12 сентября 2026 года внесены в backend и соседний репозиторий `trade_bot_webapp`. Автоматического деплоя нет. Параметры стратегии, риск и реальные торговые операции не менялись.

## Реализовано

- Две общие палитры фронтенда: светлая и тёмная. Режимы «Авто / Светлая / Тёмная», сохранение на устройстве, реакция на изменение темы. Авто использует Telegram только внутри Mini App, иначе тему ОС. Старые inline-переопределения цветов Telegram удалены.
- Короткое меню «Ещё», отдельные страницы подключения OKX и состояния сервиса. Торговля аккаунта отделена от состояния процесса.
- Компактная двухколоночная форма стратегии сохранена; добавлено подтверждение ухода с несохранённым черновиком.
- Новый авторизованный `GET /api/service/status`: подготовка, прогресс, число инструментов, БД, свежесть всех обязательных таймфреймов, время проверки, запуск и версия. Ответы не кэшируются, проверка БД ограничена 1,5 секунды.
- Рыночный timestamp — наиболее старое наблюдение по обязательным таймфреймам 1m/LTF/HTF. Пропавший HTF не маскируется живым 1m. Свежесть проверяется по входящим обновлениям, включая незакрытую свечу, а не только по закрытиям.
- Интерфейс опрашивает состояние каждые 15 секунд, пока видим. Ошибка запроса или возраст ответа больше 45 секунд снимают зелёный статус. Таймаут запроса — 6 секунд. Данные рынка старше 90 секунд означают деградацию после прогрева.
- Последние 50 смен состояния подготовки доступны в интерфейсе. Добавлены PostgreSQL-хранилище и миграция `0006_service_status_events.sql`; при недоступной таблице используется память текущего процесса, что явно обозначено в UI. Это журнал подготовки, не аудит всех сбоев биржи.
- Штатные сообщения старта/прогрева/готовности не отправляются в Telegram. Ошибка подготовки и восстановление после неё уведомляют однократно за инцидент. Недоставка Telegram не блокирует готовность; прогресс-горутинa завершается до публикации финального состояния.
- `/api/strategy/*` защищён серверной проверкой администратора. `/api/me` сообщает `is_admin`, фронтенд больше не определяет права по публичной переменной окружения.
- Тестовый вход `/api/dev/session` закрыт по умолчанию и в production.
- На странице стратегии показаны сохранённые настройки с серверными ограничениями V3 по риску, позициям и shorts. Черновик не выдаётся за применённую конфигурацию.
- Состояние показывает фактически выбранные монеты, список, размер базового списка и запрошенной динамической выборки. Свежесть проверяется отдельно для каждой монеты по всем обязательным ТФ. Пропавшая монета снимает общую готовность.
- `GET /api/settings` больше не возвращает ключи OKX, только признак наличия полного комплекта. Отдельный авторизованный `POST /api/connection/okx` принимает все три значения и не возвращает секреты. Обычное сохранение настроек сохраняет действующие ключи. В форме секреты скрыты, не предзаполняются и очищаются после сохранения; статус наличия ключей не означает проверку биржей.
- Анонимный `GET /ready` возвращает 200/503 без данных аккаунта. Он подготовлен для внешнего монитора; сам монитор пока не подключён.

## Проверка

Backend: `go test ./...` и `go test -race ./...` (Go из `go.mod`). Есть регрессионные тесты на тихий старт, ошибки Telegram, однократное восстановление, копирование/ограничение журнала, пропавший таймфрейм, состояния health API, права администратора и dev-вход.

Frontend: `npm run check`, `node --experimental-strip-types --test tests/*.test.mjs`, `npm run build`.

Изолированный UI-тест в репозитории фронтенда:

1. `node tests/mock-api.mjs`
2. `PUBLIC_API_BASE=http://127.0.0.1:5190 npm run dev -- --host 127.0.0.1 --port 5191 --strictPort`
3. `node tests/browser-smoke.mjs`

Тест использует новый временный профиль локального Chrome, вымышленные данные и запрет торговых изменений. Проверяются обе темы, сохранение выбора, авто-тема ОС, ширины 320/390/768/1280, несохранённый черновик, недоступность сети, устаревшие данные, восстановление, серверные ограничения, список монет и безопасная ошибка сохранения новых ключей. Скриншоты сохраняются во временный каталог. В тестовом API нет подключений к OKX, Telegram и БД. Backend-тесты дополнительно проверяют редактирование ключей и журнал через подменное хранилище; SQL-миграция на настоящем PostgreSQL в этой работе не запускалась.

## Порядок выкладки

1. Проверить серверный `ADMIN_TELEGRAM_USER_ID`. Если переменная не задана, используется существующий администратор Telegram-бота. Пустое/неверное явно заданное значение запрещает доступ всем. Публичный `PUBLIC_ADMIN_CHAT_ID` больше не даёт прав в веб-интерфейсе. Переменная сервера пока относится только к веб-API; старые Telegram-команды сохраняют прежнего администратора.
2. В production не включать `ENABLE_DEV_AUTH`. Для реального локального backend dev-вход требует одновременно `APP_ENV=local` или `dev`, `ENABLE_DEV_AUTH=true`, положительный `DEV_TELEGRAM_USER_ID`. Для UI-проверок предпочтителен изолированный mock API.
3. В старом коде проверка среды у dev-входа была закомментирована. Если эта версия публиковалась, при выкладке заменить `JWT_SECRET`, чтобы отозвать ранее выданные токены. Это завершит текущие веб-сессии; потребуется снова открыть Mini App. Секреты в репозиторий не добавлять.
4. Применить миграцию `0006_service_status_events.sql` штатным процессом миграций с резервной копией БД. Затем согласованно выпустить backend и frontend: новый UI требует нового API, а старый UI больше не сможет менять ключи через обычные настройки. Проверить реальный вход из Telegram, 403 для обычного пользователя на тюн и 404 на dev-вход в production.
5. Проверить подготовку, свежесть таймфреймов и восстановление после сетевой ошибки без тестовых реальных ордеров. Убедиться, что торговые уведомления продолжают приходить, а штатный прогрев — нет.

## Что ещё требует отдельного шага

- Выкладка, миграция и независимый внешний монитор `/ready` с выбранным получателем уведомлений. Остановленный процесс не может сам сообщить о падении. Проверку готовности не следует бездумно превращать в автоматический рестарт контейнера при временном сбое рынка.
- Полный журнал эксплуатационных инцидентов, политика хранения старых записей и шифрование секретов в БД. Write-only веб-контракт не заменяет шифрование хранения.
- Дальнейшее упрощение админской статистики и группировка повторяющихся торговых reject-уведомлений. Уведомления о сделках не изменялись.

Статус «Система работает» означает успешную подготовку, доступную БД и свежие входящие рыночные потоки. Он не гарантирует наличие сигналов, открытие сделки, доступность приватного API каждого пользователя или доходность стратегии.

## Исправление прогрева — 12 сентября 2026

- Причина остановки после старта в 11:00 МСК: OKX включает текущую незакрытую свечу в `limit`, а прогрев требует полное количество закрытых свечей. Запрос 230 возвращал только 229 подходящих свечей.
- `GetCandles` теперь запрашивает запасную строку, при необходимости догружает более старые страницы (не более 300 строк за запрос), исключает незакрытые/некорректные свечи и дубликаты, возвращает последние N свечей по времени.
- Неуспешный прогрев повторяется через 30 секунд до успеха или остановки процесса. Готовность не выставляется при ошибке или отмене. Подробности ошибок включают символ, таймфрейм и фактическое/требуемое число свечей.
- После выкладки проверить лог `warmup done` и HTTP 200 на **`/ready`**. Это торговая готовность с проверками прогрева, БД и свежести рынка; `/readyz` — отдельный старый инфраструктурный маршрут. В Coolify проверка здоровья на момент диагностики выключена. Не включать автоматические рестарты из-за временного отсутствия рыночных данных.
- Проверка публичного API без запуска торговли: `TEST_OKX_PUBLIC_CANDLES=1 go test -count=1 -run '^TestGetCandlesOKXIntegration$' -v ./internal/modules/okx_websocket/service`.
- Таймаут записи истории статуса и недоступность внешних портов фронта/бэка требуют отдельной проверки инфраструктуры; исправление прогрева не доказывает устранение этих проблем. Не менять торговые лимиты для обхода ошибки прогрева.
