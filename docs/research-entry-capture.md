# Снимки входов для исследования выходов

Реализован opt-in capture новых входов. Это не новая стратегия, не исправление
закрытия ARB и не сборщик исторических котировок. Входы, риск, SL/TP, runner,
список монет и Telegram-уведомления не меняются.

## Включение

По умолчанию выключен: `RESEARCH_CAPTURE_ENABLED=false`.
Для отдельно согласованного запуска нужны `RESEARCH_CAPTURE_ENABLED=true` и
`RESEARCH_PROTOCOL_ID` (1–64 ASCII буквы/цифры, `_`, `-`). Не использовать секрет
или идентификатор аккаунта в качестве protocol ID. Ошибочная настройка отключает
только capture и выводит фиксированный код ошибки без её значения.

До запуска нового бинарника, даже с выключенным capture, обязательна additive
миграция `0008_add_research_entry_snapshot.sql`: новый INSERT использует колонку.
Этот документ не запускает миграцию или деплой.

## Контракт данных

`trade_history.research_entry_snapshot` — nullable JSONB, отдельно от payload.
Обычные update/close и API Get/List её не читают/не изменяют. Старые строки
остаются NULL; нет backfill. Ошибка UUID/сериализации/размера даёт NULL,
агрегированный счётчик и тот же один INSERT сделки. Ошибка самого INSERT
по-прежнему возвращается вызывающему коду; дополнительных повторов нет.

Формат: `{ "payload": { "schema": 1, ... }, "checksum": "sha256-hex" }`.
Checksum рассчитан по компактному JSON typed payload в порядке полей builder.
PostgreSQL JSONB меняет порядок ключей: нельзя проверять хеш по `jsonb::text`.
Будущий collector должен восстановить канонический порядок модели, UTC-время
и отсортированные причины. Checksum доказывает только неизменность содержимого.

Максимум 32768 байт, включая envelope. Только whitelist полей:

- Случайный capture UUID, protocol ID, инструмент/сторона/TF, revision/dirty/unknown.
- Planned до корректировки по fills и actual после существующего исполнения.
- Raw metadata из использованного ответа и effective floats, время его получения.
  Нет дополнительного запроса, выдуманного exchange timestamp или raw из float.
- Raw/effective BE, LOCK, partial, time и все stale-поля, включая false/0;
  effective stale использует существующий `GetStaleConfig`.
- Отдельные наблюдения существующих чтений calc/sizing/open. Разные relevant
  hashes → `settings_changed_during_entry`, не единый выдуманный конфиг.
- Источник времени, первый/последний fill, количество и наблюдаемый объём.

`complete` означает полноту захваченных наблюдений, а не сверку с архивом биржи.
`reported_complete` — результат существующего ожидания fills с проверкой
наблюдаемого объёма. Timeout, короткий/неоднозначный объём, разные времена fills,
неизвестная сборка/metadata дают incomplete. Сумма floats не исправляется
молча до ожидаемого размера; точная decimal-сверка принадлежит collector.
Локальное fallback-время не называется биржевым.

Существующая торговая `FillTime` берётся из OKX `ts` (время записи), и capture
не меняет эту семантику. Настоящее время исполнения из `fillTime` сохраняется
отдельно только для исследования; `FirstFillAt`/`LastFillAt` используют его.
Источник времени входа обозначается `exchange_record`. Отсутствующий или
невалидный `fillTime` даёт `fill_time_missing`, отличие последнего исполнения
от торгового времени входа — `entry_time_not_execution`; оба случая incomplete.
Источник различия полей: [OKX transaction details](https://www.okx.com/docs-v5/en/#order-book-trading-trade-get-transaction-details-last-3-days).

Нет Settings целиком, API-ключей, DSN, account/Telegram/order/private trade IDs
или текстов приватных ошибок. Research-снимок исключён из JSON TradeRecord.
Счётчики доступны через существующий ExecutionStats: `research_capture_complete`,
`research_capture_incomplete`, `research_capture_failed`, `research_capture_disabled`
и фиксированные `research_capture_error_*`. Дополнительных Telegram-сообщений нет.

## Проверки

Требуется Go 1.27.0 по go.mod. На машине с `GOTOOLCHAIN=local` и Go 1.26.7:
`GOSUMDB=sum.golang.org GOTOOLCHAIN=go1.27.0 go test -race ./...`.
При sandbox-ограничении cache задать GOCACHE внутри отдельного temp-каталога.
Sonic на Go 1.27 предупреждает о fallback к encoding/json; warning не скрывать.

Интеграционные тесты принимают только явно заданный `TRADE_REPORT_TEST_DSN`
с host `127.0.0.1`, database `trade_report_test`. Это одноразовая локальная БД,
никогда production. Не вставлять реальные пароли в командную строку/документы.

```sh
go test -p 1 ./internal/modules/repository/pg ./internal/modules/runner_old/sessions -run 'Test(ResearchSnapshotPostgresCompatibility|CaptureOnOffTradeParity)' -count=1 -v
go test ./internal/modules/repository/pg -run '^$' -bench BenchmarkResearchSnapshotInsert -benchmem -count=5
```

Первый тест проверяет старый INSERT, SQL NULL, сохранность снимка при Update/Close.
Второй — реальный session/SQL и fake HTTP, одинаковые вызовы входа/SL/TP и
аварийного закрытия при capture on/off. Настоящих ордеров тест не отправляет.
Benchmark сравнивает NULL, 4KiB и near-limit запись. Это локальная оценка
накладных расходов, не гарантия нулевого влияния в production. SKIP не равен PASS.

## Gate перед production

1. Проверить архивные исполнения/учёт ARB отдельно. Не считать capture его исправлением.
2. Выполнить локальные PostgreSQL/parity-тесты и сохранить результат benchmark.
3. Получить отдельное согласование backup и additive-миграции; проверить старый бинарник.
4. Согласовать deployment, protocol ID и контрольную малую выборку; capture сначала off.
5. После включения проверить размер/INSERT latency, counts incomplete/failed и содержимое
   безопасного снимка. При проблемах выключить flag; snapshot не удалять.
6. Откат приложения — старый бинарник, сохранённая новая колонка. `goose Down`
   удаляет данные и не является процедурой обычного rollback.
7. Collector, read-only ключ/роль, приватный volume, 28-дневный период и replay v2
   требуют отдельного следующего этапа. Не подавать snapshot в legacy replay v1.

## Offline collector core — 8 октября 2026

Первый слой `internal/research/collect` — чистые функции для будущего collector,
не фоновый процесс и не новый режим торговли. Эти функции не читают БД,
не вызывают OKX и не меняют позиции. Позднее добавленные I/O-адаптеры описаны
ниже; включать capture только ради наличия пакета не нужно.

- `DecodeSnapshot(raw, protocol)` проверяет снимок через существующий producer:
  checksum, полный набор полей, статус и причины. Перестановка ключей в JSONB
  допустима; дубли, неизвестные/пропавшие поля, изменение значения и превышение
  32 KiB отклоняются. `complete` относится только к capture, не к архиву OKX.
- `Reconcile(input)` сверяет исполнения с явно переданными entry/exit orders.
  Объёмы, комиссии, realized PnL и funding складываются как точные десятичные
  числа без float. Один entry order может иметь несколько fills; несколько
  entry orders пока отклоняются как неоднозначная атрибуция. Исполнения входа
  в разные моменты отмечаются `multi_time_entry`: единый replay-вход из них
  автоматически не строится.
- `PlanSegments(entry)` создаёт полуоткрытые интервалы ровно на 72 часа.
  Для входа внутри минуты это 4319 полных минут и два граничных интервала,
  а не свеча до входа и округлённый горизонт.
- `BoundaryOHLC(segment, ticks, sourceComplete)` исключает правую границу и
  повторные ticks. Пустой подтверждённый интервал имеет `prices: null`;
  неподтверждённое отсутствие ticks остаётся `incomplete`. Разные цены с
  одинаковым timestamp не получают выдуманный порядок: `tick_order_ambiguous`.

### Контракт доверия для адаптеров

`ArchiveComplete`, `Funding.Complete` и `sourceComplete` — утверждения
вызывающего адаптера, не результат сетевой проверки внутри core. Адаптер должен
доказать пагинацию/покрытие, принадлежность аккаунту и конкретной позиции,
временные границы и единицы до их установки. Отсутствие записей не доказывает
нулевой funding. `RecordedTradingNet` — только результат без funding;
сравнивать суммы из разных областей учёта запрещено.

Статусы независимы: `reconciliation=pending|matched|mismatch`,
`costs=unknown|sensitivity-only|verified`, покрытие рынка и статус capture.
`matched` не означает готовность к replay или проверку live-позиций. Итоговый
`reconciled_trading_net_usdt` появляется только для полностью сверенного
закрытия с комиссиями в USDT; полный `reconciled_net_with_funding_usdt` —
только с подтверждённым funding в USDT. Неполный архив и расхождения не дают
итоговый net. Наблюдённые суммы/исполнения не являются подтверждённым результатом.

`Fill` и `LedgerInput` содержат приватные идентификаторы только в памяти и
отказывают в JSON-сериализации. Не логировать их через fmt, reflection или
структурный logger: запрет JSON не является защитой от всех видов логирования.
Для результата использовать только whitelisted `LedgerReport`; ошибки core
содержат фиксированные коды. Нормализация рассчитана на USDT SWAP; неизвестная
валюта комиссии не конвертируется в USDT. Лимиты: 100000 fills/ticks, 10000
exit orders, не более 32 целых и 32 дробных цифр входного числа.

### Что ещё не реализовано этим этапом

Read-only DB/OKX adapters, отдельные Read credentials, безопасная пагинация и
квоты, приватное хранилище с атомарными записями/checksum/lock, автоматический
сбор 28 дней + 72 часа, валидатор bundle и replay v2. До них core не собирает
реальные данные и не даёт оснований выбирать прибыльную стратегию A/B/C.

Локальная проверка core: unit tests и `go test -race -p 1 ./... -count=1`,
`go vet ./internal/research/collect ./internal/modules/telegram_bot/...`,
`go build ./cmd/...` на Go 1.27 — PASS. Внешние opt-in тесты и PostgreSQL
integration tests в этом прогоне не включались; production не проверялся.

Self-review и независимое ревью core выявили потерю точности в сравнении JSON:
изменение `2` на `2.00000000000000001` могло пройти через float64. Исправлено
точным сравнением рациональных чисел с ограничением длины/экспоненты; regression
сначала воспроизвёл дефект, затем прошёл. Дополнены проверки изменённого размера
дубликата fill и выхода до первого фактического исполнения входа. Других
существенных замечаний в scoped core не найдено; адаптеры и live-сбор этим
ревью не подтверждены.

## Collector I/O primitives — 8 октября 2026

Следующий локальный слой (`store.go`, `archive_http.go`) работает только на
Linux/macOS. Он ещё не является `cmd/research-collect` и не подключён к runner.

### Приватное хранилище

`OpenStore(dir, maxBytes)` требует уже существующий абсолютный каталог владельца
с правами 0700, вне git. Symlink-пути, hardlink-файлы, нештатные типы файлов и
неприватные права отклоняются. Применяется эксклюзивный OS lock; второй writer
не стартует. Каталог должен находиться на отдельном локальном приватном volume
вне любого web-root: последнее нельзя достоверно определить по файловой системе,
это обязательная проверка оператора перед запуском. NFS и прочие файловые системы
без надёжных flock/link/fsync не поддерживаются.

`Put` принимает только JSON до 4 MiB и возвращает SHA256 reference; `Get`
проверяет schema/checksum. Публикация — sync временного файла, атомарный hard link
без замены назначения, удаление временного имени и sync каталога. Это намеренно
не обычный rename с перезаписью. Старые версии не изменяются. Повторный Put
идентичного JSON после удаления незначащих пробелов идемпотентен; порядок ключей
и числовая запись на этом уровне не нормализуются. Файлы имеют права 0600.

Бюджет ограничен 1 GiB (можно задать меньше); учитываются старые объекты,
журналы квот и `.pending-*` после обрыва. Максимум 100000 файлов — дополнительный
предохранитель от неограниченного сканирования. Место под новые имена (включая
temp + final и новый суточный журнал/lock) проверяется до записи; append и
идемпотентный Put не требуют нового имени. Коррупция при reopen блокирует
работу; автоматического исправления/удаления нет. Обрыв между link и удалением
временного имени может оставить два hard link: такой каталог также блокируется
до ручной проверки. Ошибка sync означает неизвестный итог публикации: сначала
проверить объект повторным Get, а не объявлять его сохранённым.

Store — механизм записи байтов, **не фильтр персональных данных**. В него
разрешено передавать только результат whitelist-нормализации/bundle, не private
HTTP responses, DSN, credentials или сериализованный рабочий контекст. Будущий
bundle writer должен обеспечивать эту границу. Каталог/lock/quota нельзя удалять
между проходами: это уничтожает историю бюджета и защиту от второго writer.

`ReserveRequest` сначала сохраняет и синхронизирует последовательную запись
суточного UTC-журнала, только затем разрешает отправку. Лимит — 10000 попыток
в сутки, включая retries; сохраняется после reopen. Обрыв после reservation
может списать неотправленный запрос, но не даёт бесплатный повтор. Повреждённый
журнал блокирует работу. Пустой файл означает, что ни одна попытка ещё не была
разрешена. Диск заполнен — новые обращения прекращаются, торговый бот не затронут.

### Public archive client

`NewArchiveClient(store).Get(ctx, path, query)` разрешает только HTTPS
`www.okx.com` и четыре публичных GET endpoint: `history-candles`,
`history-trades`, `history-mark-price-candles`, `funding-rate-history`.
Пути сверены с [официальной документацией OKX](https://www.okx.com/docs-v5/en/).
Разрешены только необходимые query-поля, USDT-SWAP instruments, свечи 1m и
limit 1–100; приватные и торговые endpoints отсутствуют. Произвольный URL,
заголовки, credentials, proxy, redirects и cookies не принимаются.

Запросы одного Store сериализованы; в течение его жизни между стартами не менее
1s. Каждый attempt имеет timeout 15s, response body до 4 MiB и headers до 32 KiB.
Для сетевого сбоя, 429, 500/502/503/504 предусмотрены максимум 3 повтора с
backoff 2/4/8s и учётом Retry-After. Ожидание более 60s/непонятный Retry-After
возвращает `archive_retry_later` без преждевременного повтора. Отмена действует
на очередь, backoff и запрос. Внутреннее повторение GET на переиспользованном
соединении отключено: иначе net/http мог сделать дополнительный запрос без
reservation. Каждый явный retry проходит через суточный журнал.

Срок Retry-After сохраняется как общий not-before для всех клиентов одного
Store: возврат ошибки, отмена и исчерпание retries его не сбрасывают. Если
оставшаяся пауза больше 60s, новый вызов возвращает `archive_retry_later` без
запроса; при меньшей паузе ожидает остаток. С 9 октября срок и минимальный
интервал сохраняются на диске; поведение при перезапуске описано ниже.

Ошибки имеют фиксированные коды, без raw URL/body/ошибки транспорта. Успех
проверяет JSON envelope `code=0`, `data` как массив; содержимое ещё должно пройти
endpoint-specific нормализацию. HTTP200/пустой data не доказывает полноту архива.
Client ничего не сохраняет автоматически. Биржевой ненулевой code внутри
HTTP200 даёт `archive_api_error`, без автоматических повторов.

### Оставшаяся интеграция

После добавленного 9 октября PostgreSQL adapter нужны отдельная приватная OKX авторизация через
Read credentials, пагинация с проверкой 200-page бюджета/дубликатов/покрытия,
manifest и whitelist bundle writer, CLI и согласованный запуск. Public funding
rates не заменяют подтверждённые funding списания позиции. Не включать capture
и не объявлять сбор 28 дней запущенным по наличию этих I/O primitives.

Проверки I/O-этапа: полный `go test -race -p 1 ./... -count=1`, vet изменённых
Go-пакетов, `go build ./cmd/...` и компиляция collector под Linux/amd64 — PASS.
Тесты включают реальные временные файлы/OS lock и локальный TLS-сервер, но не
реальные запросы к OKX. PostgreSQL opt-in integration tests не включались;
проверка Linux была компиляцией, не runtime-тестом production-filesystem.

Self-review исправил несовпадение checksum при HTML-экранировании JSON,
неучтённые автоматические повторы net/http и зависание при zero-value Store.
Независимое ревью выявило два существенных дефекта: потерю Retry-After между
вызовами и успешную запись за пределом file-count limit. Оба воспроизведены
regression-тестами до исправления; после исправлений полный race-прогон прошёл.
Неисправленных существенных замечаний в рассмотренном I/O-коде не осталось.
Совокупный Telegram/UI batch, actual OKX permissions и будущие адаптеры это
ревью не подтверждает. Перед выкладкой всё равно нужны проверка конкретного
релиза/конфигурации, согласованный доступ/volume и проверка после deploy.

## Restart safety и DB adapter — 9 октября 2026

### Устойчивая пауза запросов

Store ведёт приватный append-only `.requests`: начало перед сетевым вызовом,
завершение с общим сроком следующего запроса сразу после ответа/ошибки.
Каждая строка имеет checksum, fsync файла и каталога. Дедлайн не уменьшается;
после reopen восстанавливаются как Retry-After, так и минимальный интервал 1s.
Этот журнал ограничен 64 MiB и входит в общий дисковый бюджет; при переполнении
сборщик останавливает исследовательские запросы, не удаляет историю.

Обрыв после начала запроса, пустой/оборванный/повреждённый журнал блокирует
reopen: неизвестно, успела ли биржа выдать длительный Retry-After. Ошибка записи
блокирует новые HTTP-вызовы и в текущем процессе. Нельзя автоматически удалить
журнал и запустить заново: нужна ручная проверка причины, сохранение исходных
файлов и консервативное решение о восстановлении; автоматический repair ещё
не реализован. Потерянная попытка может расходовать квоту без отправки.

Старый каталог без `.requests` открывается новой версией; старый бинарник
отклонит каталог с новым журналом. Для rollback не удалять журнал ради
совместимости. Защита не рассчитана на злоумышленника с правами владельца/root,
ручное удаление каталога или изменение системного времени вперёд.

### Чтение снимков PostgreSQL

`ReadEntries(ctx, pool, EntryWindow)` делает один короткий read-only
repeatable-read проход: context/statement timeout 5s, lock timeout 1s.
Сеть OKX не вызывается внутри транзакции. Pool передаётся явно и должен
использовать отдельную ограниченную роль, не pool торгового приложения.
Отмена/ошибка scan/query/commit не возвращает частичный успешный batch;
rows закрываются до commit, rollback имеет собственный ограниченный context.

Фиксированный контракт view `research_collect.entries_v1`:

| Поле | Тип | Источник при отдельной подготовке view |
| --- | --- | --- |
| row_id | uuid | trade_history.guid, только в памяти |
| inst_id | text | trade_history.inst_id |
| status | text | trade_history.status |
| entry_at | timestamptz | trade_history.entry_at |
| open_order_id | text | payload->>'open_order_id', только в памяти |
| research_entry_snapshot | jsonb nullable | неизменяемая колонка capture |

Оператор отдельно создаёт account-scoped security-barrier view с фиксированным
фильтром одного согласованного аккаунта и ролью с USAGE schema + SELECT только
этого view. У роли не должно быть доступа к базовым таблицам, `user_settings`,
чужим аккаунтам или записи. Адаптер **не создаёт view/роль и не доказывает их
реальные права**: это обязательная проверка перед запуском. Секреты/DSN адаптер
не ищет и не пишет; создание pool и безопасная передача credentials — будущий CLI.

Окно включения полуоткрытое `[From,To)`, максимум 28 дней, лимит 1–1000 строк.
Границы должны быть кратны микросекунде: более точные значения отклоняются до
запроса, иначе pgx усечёт параметр и может незаметно исключить граничную строку.
SELECT запрашивает limit+1, сортирует по entry_at,row_id; превышение отмечается
`truncated=true`. Это не полнота всей выборки: если строки с одним timestamp
не помещаются в лимит, нельзя продвинуть время и молча пропустить остаток.
Следующая интеграция должна сообщать incomplete, а не создавать private cursor
на диске. Временной диапазон БД не доказывает биржевое время исполнения.

SQL ограничивает размер возвращаемого JSON 32 KiB, ID ордера 128 байт, symbol
40 байт, status 16 байт. Missing snapshot учитывается отдельно от некорректного
или oversized. Проверяются checksum/protocol, symbol и время строки (с учётом
микросекундной точности PostgreSQL). Повтор capture ID делает обе записи invalid;
их нельзя считать двумя независимыми входами. Отсутствующий order ID означает
`attribution_pending`, даже если capture complete. Нормализация JSONB, увеличившая
представление сверх лимита, консервативно считается invalid, не исправляется.

Внутренние строки и batch отказывают в JSON и скрываются при fmt-formatting;
сериализуется только `EntryCoverage` с агрегатами. Не обходить это reflection,
unsafe или logger-адаптерами. Capture complete не означает ledger matched,
costs verified или разрешение подавать данные в replay v1.

Локальный integration-тест принимает только `RESEARCH_COLLECT_TEST_DSN` на
127.0.0.1, БД `trade_report_test`, без fallback-hosts. Создаёт только синтетические
таблицу/view/роль в одноразовой БД и удаляет свои fixtures после теста.
Проверяет account scope, запрет доступа к таблице/записи, реальную изоляцию при
конкурентном update, повторный проход, JSONB и лимиты. Production этим не проверен.

Результат проверки 9 октября: PostgreSQL17 integration PASS (не SKIP), полный
`go test -race -p 1 ./... -count=1` с локальными DB-тестами PASS после итогового
исправления границ времени; vet изменённых Go-пакетов, `go build ./cmd/...`,
Linux/amd64 compile collector и diff whitespace-check PASS. Linux runtime и
реальные OKX-запросы не проверялись. Внешний opt-in тест свечей не включался.
Self-review воспроизвёл пропуск граничной строки из-за усечения pgx до микросекунд;
добавлена валидация и regression RED→GREEN на настоящем PostgreSQL. Независимый
review новых адаптеров не нашёл оставшихся Critical/Important/Minor замечаний.
Это не ревью всей накопленной Telegram/UI-поставки и не гарантия отсутствия багов.

### Приватный read-only архив исполнений OKX

Добавлен библиотечный `PrivateClient`; он не подключён к торговому процессу и
не запускается автоматически. Перед каждым `CollectFills` выполняется GET
`account/config`: ровно одна запись, `perm=read_only`, UID совпадает с явно
переданным ожидаемым аккаунтом. Изменение прав между проходами блокирует следующий
сбор. Это не проверка реальных production-ключей или соответствия аккаунту view БД.

`ReadPrivateCredentials(ctx, file)` принимает только явно унаследованный pipe FD,
JSON до 4096 байт, максимум 5 секунд (либо более короткий context). Обязательны
`api_key`, `secret_key`, `passphrase`, `expected_uid`; дубли, неизвестные поля,
обычные файлы и управляющие символы отклоняются. FD закрывает вызывающий код.
Не передавать значения через argv, env, документацию или журналы. Буфер очищается
best-effort: Go не гарантирует стирание всех копий строк/криптографических данных.
Приватные типы запрещают JSON и скрывают содержимое при fmt; это не защита от
reflection/unsafe, debugger или логгера, который обходит эти интерфейсы.

Подпись HMAC-SHA256/Base64 создаётся заново для каждой HTTP-попытки, включая
полный query. Разрешены только фиксированные HTTPS GET `account/config` и
`trade/fills-history`; публичный клиент не получает авторизацию. Лимиты,
durable cooldown и квота Store общие для публичного и приватного клиентов.
Редиректы, proxy и cookies не используются; ошибки не содержат тело ответа.

Окно fills относится к **`ts` записи**, а цена/время исполнения — к **`fillTime`**.
Границы `[From,To)` кратны миллисекунде, ширина не больше 31 дня, начало не старше
80 дней, конец не в будущем. Это консервативное ограничение внутри last 3 months.
Из-за неоговорённой включительности границ API запрашивается begin=From−1ms,
end=To, затем точный полуоткрытый диапазон применяется локально.

Пагинация идёт по числовому billId, не timestamp; максимум 200 страниц по 100
строк. Даже короткая страница не доказывает завершение: нужна пустая следующая.
Совпадающие записи дедуплицируются; конфликт, отсутствие прогресса, некорректные
поля, отмена, квота или исчерпание страниц дают incomplete. Весь некорректный
page отвергается, ранее принятые данные не считаются полным архивом. Нет order ID —
нет безопасной атрибуции: такие записи пока не поддерживаются. Валюта комиссии
сохраняется, неизвестная/не-USDT валюта не конвертируется в USDT автоматически.

Только агрегатный `FillCoverage` допускает сериализацию. Сырые ответы, bill/order
ID и приватный cursor не сохраняются; повторный запуск перечитывает окно.
`record_window_complete` означает только исчерпание данного API-окна, не полную
историю позиции, не доказательство полноты funding и не `LedgerInput.ArchiveComplete`.
Отдельный адаптер ещё должен доказать связь с ордерами/позицией и покрытие затрат.

Контракт сверен 9 октября с официальной документацией OKX:
[account config](https://www.okx.com/docs-v5/en/#trading-account-rest-api-get-account-configuration),
[fills history](https://www.okx.com/docs-v5/en/#order-book-trading-trade-get-transaction-details-last-3-months),
[REST authentication](https://www.okx.com/docs-v5/#overview-rest-authentication).
Далее нужны market/funding pagination, атрибуция, безопасная сборка bundle и CLI;
до отдельной подготовки read-only доступов и проверок запускать сбор нельзя.

Проверки этого среза: приватные сценарии и полный Go race-прогон PASS; vet
collector, сборка cmd, Linux/amd64 compile и whitespace-check PASS. Opt-in БД и
внешние API в этом прогоне не запускались. Общий `go vet ./...` не чистый: три
существующих замечания runner_old (unkeyed PosKey и два копирования Base с mutex),
подтверждённые на HEAD, не исправлялись в рамках research-адаптера.
Self-review исправил неверный complete при отмене одновременно с пустой страницей;
независимый review нашёл неоднозначные JSON-поля разного регистра. Обе проблемы
воспроизведены RED→GREEN. Теперь credential-поля требуют точного имени, а алиасы
известных полей приватных ответов отклоняются до структурного decoding.
Независимый review не сообщил других блокирующих или minor-замечаний; исправления
проверены тестами, повторное независимое ревью не проводилось. Production не проверен.

### Публичные свечи и realized funding

`ArchiveClient.CollectCandles(ctx, MarketWindow, "trade"|"mark")` загружает
закрытые 1m свечи в отдельные ряды. Окно `[From,To)` не более 72 часов, начало
не старше 80 дней, конец не в будущем. Границы свечного окна должны совпадать с
началом минуты: округлять EntryAt или заменять первую/последнюю частичную минуту
полной свечой нельзя. Для этих сегментов используется отдельный адаптер публичных
сделок, описанный ниже.

Проверяются confirm=1, закрытие свечи к началу прохода, минутный timestamp,
десятичные цены/объёмы и геометрия OHLC. Нулевые объёмы сохраняются как полученное
наблюдение. Пропуски не заполняются предыдущей ценой. `expected_minutes` и
`missing_minutes` показывают полноту сетки; даже пустая успешно прочитанная
история не является полным рынком. Mark OHLC не доказывает settlement mark.

Первый запрос свечей использует after=To−1ms, чтобы не захватить незакрытую
свечу в To; на минутной сетке это не исключает ни одной требуемой свечи.
Funding использует after=To+1ms и локальную фильтрацию, поскольку событие
может приходиться на произвольную миллисекунду, в том числе To−1ms.

`CollectFunding(ctx, MarketWindow)` сохраняет только фактические `realizedRate`
и `fundingTime` инструмента, не подставляя прогнозный `fundingRate`. Миллисекундные
границы допускаются без округления. Нулевая/отрицательная ставка допустима;
фиксированный восьмичасовой график не предполагается. Неизвестные поля ответа
не экспортируются, алиасы известных полей разного регистра отклоняются.

Оба адаптера используют общий ограниченный обход timestamp-страниц: до 200
страниц по 100 строк, точные полуоткрытые границы, дедупликация и сортировка.
Короткая страница не завершает обход. Пустая страница либо наблюдение ниже From
даёт `window_traversed`, но не гарантию отсутствия пропусков у провайдера.
Повтор без прогресса, конфликт одного timestamp, некорректный page, отмена,
HTTP-ошибка или лимит дают incomplete. Некорректная страница отвергается целиком;
раньше прочитанные записи остаются явно неполными. Raw response не сохраняется.

Для funding `coverage.status=complete` означает только завершённый обход API,
`schedule_verified` всегда false. `costs` — unknown при отсутствии ставок,
иначе sensitivity-only, даже если ставки наблюдались частично. Это не сумма
списаний аккаунта и не `FundingEvidence.Complete`; в ledger напрямую не подавать.
Исторические архивы API не обещают согласованный неизменяемый snapshot:
повторные проходы могут дать другие наблюдения. Нужны отдельные источники
полноты расписания, settlement mark и атрибуции фактических затрат.

Использованные публичные контракты: [свечи OKX](https://app.okx.com/docs-v5/en/),
[mark/funding OKX](https://app.okx.com/docs-v5/zh/). На этом этапе нет записи
готового bundle, CLI, автоматического запуска или подключения к торговле.

Проверено 9 октября: полный Go race-прогон, vet collector, сборка cmd,
Linux/amd64 compile и whitespace-check PASS после исправления верхней границы.
Тест подтверждает 4320 закрытых минут за 72 часа; негативные сценарии включают
пропуски, дубли/конфликты, некорректные свечи/ставки, отмену и исчерпание бюджета.
Self-review и независимый review нашли захват live-свечи за правой границей;
ошибка воспроизведена RED→GREEN. Других функциональных блокеров review не выявил.
Замечание к формулировке cursor в плане устранено, отложенных minor нет.
Общий vet по-прежнему сообщает три старых замечания runner_old. Opt-in БД,
реальные API, Linux runtime и production не проверялись; всей поставке это
не даёт автоматического разрешения на deploy.

### Публичные сделки граничных сегментов

`ArchiveClient.CollectBoundaryTrades(ctx, MarketWindow)` читает один неполный
минутный сегмент: `[From,To)` короче минуты, не пересекает её правую границу,
обе границы кратны миллисекунде. Полные минуты остаются задачей CollectCandles.
Срок давности — не более 80 дней, конец не позже начала прохода.

Первый запрос `history-trades` ищет записи ранее To (`type=2`, timestamp).
Далее используются только `type=1` и числовой public trade ID: это позволяет
прочитать больше 100 сделок с одним timestamp. Нельзя заменить этот обход
timestamp-пагинацией или завершать его на короткой странице. Обход заканчивается
пустой страницей либо проверенной записью строго раньше From. Сделка ровно в
From включается, ровно в To исключается. Ограничения HTTP/квоты общие с остальными
адаптерами, максимум 200 страниц по 100 записей за проход.

До принятия страницы проверяются ID, инструмент, цена/размер, время, buy/sell,
источник 0/1 и непротиворечивость наблюдаемого порядка ID/времени. Повторы
дедуплицируются, конфликт или регресс дают incomplete. Неизвестные поля не
экспортируются. Public market trade ID разрешён в архиве; это не private fill ID.
Цены и размеры сохраняются исходными decimal-строками, без float-преобразования.

`coverage.window_traversed` — лишь завершение наблюдаемого обхода API, а не
гарантия отсутствия пропусков/изменений архивов у биржи. При разных ценах в одну
миллисекунду `report` и `coverage.status` остаются incomplete с причиной
`tick_order_ambiguous`; исходные сделки сохраняются, OHLC не придумывается.
Пустой успешно пройденный интервал имеет complete обход, ноль наблюдаемых сделок
и `prices=null`, а не свечу с предыдущей ценой. При прерывании данные прошлых
страниц сохраняются только как неполное наблюдение.

Контракт пагинации сверен с [официальной документацией OKX](https://app.okx.com/docs-v5/en/)
9 октября 2026. Реальные API этим этапом не вызываются. Следующие части collector:
metadata-наблюдения, атрибуция приватных исполнений/затрат, безопасный bundle и CLI.
Торговля, production, расписания и запуск сбора не меняются.

Проверки граничного адаптера 9 октября: focused RED→GREEN, два полных
`go test -race -count=1 ./...` — PASS (21 пакет с тестами), vet collector,
`go build ./...`, Linux/amd64 test compile и whitespace-check — PASS.
Self-review и независимый scoped review существенных или minor-дефектов не нашли.
Reviewer прочитал логи основных прогонов; его отдельный запуск остановился до
тестов из-за sandbox build-cache, поэтому не считается независимым прогоном.
Общий vet сохраняет три прежних замечания runner_old. Реальные API, opt-in БД,
Linux runtime и весь накопленный release этим этапом не проверены.

### Завершённый one-shot collector (9 октября 2026)

Последующие сведения заменяют формулировки «будущий CLI/bundle» выше.
`cmd/research-collect` — отдельная программа без bootstrap торгового бота.
Она не открывает/закрывает позиции и не меняет торговые настройки. Подготовка
доступов и первый реальный запуск остаются отдельным операторским действием.

Сборка: `GOTOOLCHAIN=go1.27.0 go build -o /private/tmp/research-collect ./cmd/research-collect`
(на Linux выбрать собственный каталог бинарников). `research-collect --help`
показывает три команды:

```text
research-collect init --store DIR --outside-web-root --protocol ID --start RFC3339
research-collect run --store DIR --outside-web-root --ref PROTOCOL_HASH --db-fd 3 --okx-fd 4
research-collect inspect --store DIR --ref PROTOCOL_OR_BUNDLE_HASH
```

DIR должен заранее существовать: отдельный локальный owner-only том, каталог
0700, вне git и всех web roots. Флаг — подтверждение оператором расположения,
не автоматическое обнаружение web roots. Файлы 0600, content-addressed SHA256,
атомарная публикация, один writer с flock, общий лимит 1 GiB. Не публиковать
том через веб-сервер и не добавлять его в git. `inspect` не вызывает сеть,
но берёт lock хранилища и не работает параллельно с writer.

`init` регистрирует неизменяемое окно включения 28 суток и 72-часовой горизонт
после каждого входа, максимум 200 страниц на компонент. Первую регистрацию
нельзя датировать прошлым; ID должен совпадать с capture producer. Повторная
регистрация того же протокола допустима, другого — отвергается. Ключ `--ref`
для `run` — protocol_ref, не bundle_ref. Сам collector не включает producer.

Супервизор/secret manager должен передать credentials через **унаследованные
pipe FD ≥3**, закрыв пишущие концы после отправки. Не regular files, не аргументы
процесса, не переменные окружения и не inline-секреты в shell/history:

- DB pipe: JSON с единственным полем `dsn`, явные пользователь, пароль, host,
  port, database. Удалённое подключение требует `sslmode=verify-full`, системные
  CA; `disable` допускается только для литералов 127.0.0.1/::1. Иные query options
  запрещены. Непустые PG* env запрещены; pgpass/service/client-cert discovery
  отключены. Pool максимум одно соединение, connect timeout 5s, read-only по
  умолчанию; каждая выборка дополнительно read-only repeatable-read.
- OKX pipe (необязателен): `api_key`, `secret_key`, `passphrase`, `expected_uid`.
  Только отдельный Read-only key согласованного аккаунта; проверяются `perm`
  и UID перед чтением. Без pipe reconciliation остаётся pending. Торговые
  ключи из приложения/БД не ищутся и не используются.

Размер каждого pipe ≤4096 байт, чтение ≤5s с отменой. Ошибки CLI выводят только
фиксированные коды, не DSN, аргументы, пути или raw upstream errors.
Выход 0 — завершён текущий проход, 2 — неполнота/недостающие входные данные,
1 — ошибка. Это **не** оценка прибыльности или готовности replay.

#### Подготовка DB views (только отдельным разрешённым действием)

Дополнительно к entries_v1 нужен `research_collect.order_links_v1` с полями
`row_id uuid, order_id text, role text`. Обе выборки выполняются в одной
короткой транзакции, соединение не удерживается во время HTTP.
Пример для DBA — **не автоматическая миграция и не команда для запуска как есть**:

```sql
CREATE SCHEMA research_collect;
CREATE VIEW research_collect.entries_v1 WITH (security_barrier=true) AS
SELECT guid AS row_id, inst_id, status, entry_at,
       payload->>'open_order_id' AS open_order_id, research_entry_snapshot
FROM public.trade_history
WHERE user_id = <APPROVED_ACCOUNT_ID>;

CREATE VIEW research_collect.order_links_v1 WITH (security_barrier=true) AS
SELECT DISTINCT f.trade_guid AS row_id, f.order_id, f.role
FROM public.trade_fills f
JOIN public.trade_history t ON t.guid=f.trade_guid
WHERE t.user_id = <APPROVED_ACCOUNT_ID>;

GRANT USAGE ON SCHEMA research_collect TO research_reader;
GRANT SELECT ON research_collect.entries_v1,
                research_collect.order_links_v1 TO research_reader;
```

Создать отдельную LOGIN-роль безопасным каналом, без SUPERUSER/CREATEDB/CREATEROLE/
BYPASSRLS, без membership в торговых/широких read/write ролях; ограничить CONNECT
и schema privileges. Проверить эффективные права (включая PUBLIC и наследование):
SELECT двух views разрешён, запись, базовые таблицы и user_settings запрещены.
Owner views должен иметь только необходимые права, scope — ровно согласованный
аккаунт. Collector не доказывает права/фильтр production-view автоматически.
Индексы trade_history(user_id,entry_at) и trade_fills(trade_guid,filled_at)
уже присутствуют в миграциях; DBA должен проверить план запроса на реальном объёме.

Не более 1000 входов за проход и 10000 связей; overflow явно оставляет данные
неполными. ID используются только в памяти. Один order, связанный с несколькими
сделками в batch, конфликт entry/exit или неполная выборка блокируют атрибуцию.
Закрытая строка БД сама по себе не доказывает закрытие на бирже: нужны exact-order
исполнения, покрытие record-time окна и совпадение entry/exit объёмов.
Отдельный order за пределами view/batch не проверяется глобальным сканированием:
целостность account-scoped view обязательна. Funding не выводится из отсутствия строк.

#### Bundle, повторные проходы и ограничения

`prospective-exit-bundle-v1` содержит независимые capture/market/reconciliation/
costs, ссылки на проверенные snapshots и типизированные evidence, предыдущий
bundle и время последнего успешного прохода. Неполный текущий проход не стирает
предыдущие файлы. При следующем запуске валидируются schema/checksum/ссылки;
готовые market-компоненты того же snapshot и точного окна переиспользуются
из всей проверенной цепочки, даже если промежуточный проход не имел capture.
История обходится без рекурсии, в пределах лимита файлов store; общие snapshot
и component evidence валидируются с кешем в рамках обхода. Повреждение старого
узла не игнорируется, даже если текущему проходу он напрямую не нужен.
Неполные компоненты перечитываются с начала в пределах квот, не продолжаются
по недоказанному cursor. Метаданные и приватная сверка обновляются заново.
SIGINT/SIGTERM отменяют работу; ещё не связанный с bundle артефакт может остаться
после прерывания и учитывается в квоте. Повреждённый store автоматически не чинится.

Сохраняются 72 часа рынка независимо от фактического закрытия; будущие минуты
pending, неполные граничные минуты читаются из публичных сделок. Boundary trades
разбиваются по 500 записей, чтобы не переполнить лимит одного файла. Приборные
metadata — наблюдение текущих tick/lot/min/contract/state; сравнение двух проходов
показывает замеченное изменение, но `metadata_history_verified=false` всегда.

Флаг `replay_ready=false` всегда; автоматической конвертации в replay v1 нет.
Matched ledger может показать trading net с комиссиями, но итоговый net с funding
остаётся null без независимых подтверждённых списаний. Public funding не заменяет
account bills. `last_successful_pass_at` относится только к collection, не к
доступности торгового бота. 28-дневная выборка не означает наличия биржевого
архива: private fills ограничен 31-дневным record-time окном и 80-дневной давностью;
недоступное/позднее evidence остаётся pending, старые bundle сохраняются.

Автоматический daemon/cron не устанавливается. Оператор запускает one-shot
проходы отдельно. Общие квоты HTTP: 1 GET/s, 15s timeout, до трёх transient retry,
10000 попыток/сутки, сохранение quota/backoff при перезапуске. Сеть ограничена
предусмотренными GET endpoint www.okx.com, без proxy/redirect и write API.
Контракт metadata: [OKX public instruments](https://www.okx.com/docs-v5/en/).

Откат collector: прекратить его отдельные запуски, сохранить приватный том,
затем при необходимости отдельно отозвать его Read-key/DB-роль. Торговой миграции,
изменения позиций и перезапуска live-бота этот компонент не требует.

Итоговые проверки 9 октября: `go test -race -count=1 ./...` PASS, 22 пакета
с тестами; collector 119.410s. Включён отдельный PostgreSQL17 integration,
повторный verbose-прогон подтвердил PASS, не SKIP. `go build ./...`, vet
collector/CLI, Linux/amd64 compile и native CLI init→inspect smoke PASS.
Независимый review нашёл две ошибки цепочки resume: потерю доступа к старой
готовой истории после missing capture и непроверенные ancestral evidence.
Обе исправлены RED→GREEN. Self-review дополнительно исправил inherited blocking
pipe (реальный дочерний процесс), публикацию невалидного bundle и nil-client.
Повторный полный race выполнен после исправлений; повторного независимого review

не проверены. Локальное завершение collector не является разрешением на deploy.
