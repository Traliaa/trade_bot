# Ручное закрытие из WebApp

В карточке активной сделки доступны закрытие 25/50/75% текущей позиции и полное закрытие. Действие требует подтверждения; запрос не содержит доверенных ID пользователя, инструмента или стороны — сервер берёт их из авторизации и принадлежащей пользователю сделки.

## API

- POST `/api/trades/{guid}/close`: `{"request_id":"UUID","fraction":0.5}`.
- GET `/api/trades/{guid}/close/{request_id}`: проверка исполнения без повторной отправки ордера.
- Ответ: request_id, trade_guid, fraction, size, order_id, status, message.
- Статусы: pending, accepted, unknown, filled, canceled, rejected. Accepted не означает исполнение. Canceled может включать частичное исполнение.

## Поведение

Перед отправкой фиксируется операция в PostgreSQL. Повтор одного request_id возвращает прежнюю операцию; другая активная операция той же сделки возвращается для наблюдения. Одновременно разрешена только одна незавершённая ручная операция на сделку.

Размер берётся из свежей позиции OKX, округляется вниз к lotSz и проверяется относительно minSz/maxMktSz. Поддерживается текущий режим бота: cross + long/short. Net и isolated не преобразуются автоматически. Большие позиции, превышающие maxMktSz, закрываются меньшими долями.

Отправляется market closing order с reduceOnly и clOrdId. Отклонение отдельного ордера биржей завершает операцию как rejected. Потеря ответа, сбой сохранения после отправки или неполный ответ оставляют операцию заблокированной до проверки по clOrdId. Автоматической повторной отправки нет. Не удаляйте незавершённую запись ради повтора: в состоянии unknown/pending сначала требуется сверка ордеров с биржей. Если процесс остановился между резервированием и отправкой, может понадобиться ручная проверка оператором.

После исполнения проверяется остаток, обновляется состояние сопровождения и синхронизируется история. При полном закрытии предпринимается отмена известных SL/TP; при частичном существующие reduce-only защитные ордера сохраняются. Причина manual записывается только при совпадении последнего exit-fill с ручным ордером. Ошибки сверки сообщаются отдельно и не вызывают повтор торговой операции.

Фронт сохраняет request_id в localStorage до отправки, блокирует повторное нажатие и проверяет состояние до 15 раз, затем оставляет ручную проверку. После перезагрузки наблюдение можно продолжить. Ключи карточек привязаны к GUID, чтобы перестановка списка не перенесла подтверждение на другую сделку.

Ограничения clOrdId и reduce-only сверены с [документацией OKX](https://www.okx.com/docs-v5/): историческая уникальность clOrdId не гарантируется, поэтому защита от повторов хранится в нашей БД.

## Выпуск и проверка

Перед выпуском backend требуется применить Goose-миграцию `0005_manual_close_requests.sql`, затем обновить backend и frontend. Миграция на рабочую БД в рамках разработки не применялась.

Проверены Go-тесты валидации объёма, LONG/SHORT, чужой/закрытой сделки, HTTP-авторизации и контракта, повторов после таймаута и signed reduce-only запроса. Фронт проверен svelte-check, ESLint, production build и в браузере с локальными фикстурами. Реальные ордера не отправлялись. Проверка SQL-миграции в PostgreSQL не выполнена: Docker daemon недоступен.
